# P5.3 — Harbour Manoeuvring Core

**Status:** active specification
**Integration branch:** `feat/p5.3-harbour-manoeuvring-core`
**Primary reference vessel:** Handysize

## Product objective

P5.3 turns the current harbour technical prototype into a low-speed manoeuvring game in which the player must anticipate future vessel motion.

The player should have to manage:

`approach → reduce speed → initiate turn → arrest yaw → control residual headway → parallelise → control lateral motion → controlled berth contact`

P5.3 is successful when late corrective inputs are no longer sufficient to save a poorly planned approach.

The target is a credible game-scale manoeuvring model, not CFD and not a certified nautical training simulator.

## Architectural constraints

1. Simulation remains deterministic at a fixed 30 Hz step.
2. Babylon.js rendering remains non-authoritative.
3. Campaign settlement remains authoritative outside the simulator.
4. Campaign vessel/load data feed the physics; the simulator does not duplicate campaign economics.
5. Existing 2D harbour remains available as fallback until P5.3 is accepted on real hardware.
6. Existing campaign and persistence behaviour must not regress.

## Existing baseline

The current simulator already contains:

- surge, sway and yaw state;
- class-specific vessel parameters;
- cargo-derived displacement and draft;
- simplified thrust, rudder, prop walk, wind and current;
- collision and berth detection;
- campaign arrival/settlement integration;
- deterministic benchmarks.

The current weaknesses are:

- bridge throttle behaves too directly;
- rudder produces a direct yaw moment rather than a force dependent on inflow;
- hull sway/yaw coupling is too thin;
- prop walk is a simple additive term;
- no bow thruster;
- wind/current treatment is too coarse;
- berth success is mainly geometric;
- contact severity is not based primarily on normal contact velocity.

## Target bridge controls

### Engine order

```ts
export type EngineOrder =
  | 'FULL_ASTERN'
  | 'HALF_ASTERN'
  | 'SLOW_ASTERN'
  | 'DEAD_SLOW_ASTERN'
  | 'STOP'
  | 'DEAD_SLOW_AHEAD'
  | 'SLOW_AHEAD'
  | 'HALF_AHEAD'
  | 'FULL_AHEAD'
```

Initial normalized shaft targets:

| Order | Target |
|---|---:|
| FULL ASTERN | -1.00 |
| HALF ASTERN | -0.60 |
| SLOW ASTERN | -0.35 |
| DEAD SLOW ASTERN | -0.18 |
| STOP | 0.00 |
| DEAD SLOW AHEAD | +0.15 |
| SLOW AHEAD | +0.30 |
| HALF AHEAD | +0.60 |
| FULL AHEAD | +1.00 |

These are calibration values, not physical constants.

### Rudder

Target range:

`PORT 35° … MIDSHIPS … STBD 35°`

### Bow thruster

Target command:

`-1.0 full port … 0 off … +1.0 full starboard`

The mobile control should be momentary: releasing it returns to zero.

## Propulsion model

Bridge commands are demands rather than direct thrust values.

`EngineOrder → shaftDemand → delayed shaftActual → propeller thrust`

The actual shaft state follows the demand with vessel-class response times. Ahead/astern reversal must include a neutral response phase.

Propeller thrust uses a quadratic response proxy:

`Tprop ∝ n × |n|`

Astern efficiency is lower than ahead efficiency.

## Hull dynamics target

P5.3-B separates hull response into surge, sway and yaw components.

Minimum model:

```text
Xhull = -Xu·u - Xuu·|u|·u
Yhull = -Yv·v - Yvv·|v|·v - Yr·r
Nhull = -Nr·r - Nrr·|r|·r - Nv·v
```

This must produce residual lateral/yaw motion rather than instantly following current control input.

## Rudder target

The rudder must produce a lateral force and yaw moment from local inflow, not a direct yaw acceleration.

`Vrudder = vessel water speed + propeller wash`

`Frudder ∝ Vrudder² × sin(rudder angle)`

Consequences:

- stopped vessel + STOP + hard rudder: negligible response;
- low speed + ahead kick + hard rudder: visible steering response;
- midships does not instantly erase existing yaw rate;
- counter-rudder must arrest yaw faster than midships alone.

## Prop walk target

P5.3-C introduces:

- explicit propeller handedness;
- astern-dominant transverse stern force;
- corresponding sway and yaw moment.

Prop walk must be visible with midships rudder and no environmental force.

## Bow thruster target

Bow-thruster force acts laterally at a forward lever arm.

Effectiveness must fall strongly with speed through water.

Initial game targets:

| STW | Effectiveness |
|---|---:|
| 0 kn | 100% |
| 2 kn | ~60% |
| 4 kn | <=20% |
| >=5 kn | approximately 0% |

The thruster must not behave like a second rudder at normal harbour transit speed.

## Vessel class behaviour

### Coaster

- quickest engine response;
- shortest stopping distance;
- agile yaw response;
- strong low-speed control.

### Handysize

Reference vessel for P5.3 calibration.

- obvious inertia;
- clear residual yaw;
- tactically relevant prop walk;
- useful bow thruster.

### Feeder

- higher windage;
- stronger unloaded wind sensitivity;
- higher inertia;
- useful thruster assistance.

### Panamax

- highest inertia;
- long stopping distance;
- slow yaw response;
- demands early planning;
- later suitable for tug-assisted operations.

## Load coupling

Cargo load must continue to affect:

- displacement;
- acceleration;
- stopping distance;
- turn response;
- draft.

The same manoeuvre with 10% and 90% cargo load must produce measurably different tracks.

## Environment target

P5.3-E separates water-relative and ground-relative motion.

Required navigation quantities:

- STW — speed through water;
- SOG — speed over ground;
- COG — course over ground.

Hydrodynamic forces use water-relative motion. Position uses vessel motion plus current.

Wind must provide at least:

- lateral force;
- yaw moment.

Wind response depends on vessel class and load/windage state.

## Berthing model

P5.3-F replaces the current berth rectangle/heading/speed gate with explicit berth-coordinate metrics.

```ts
export type BerthingMetrics = {
  longitudinalErrorMeters: number
  lateralDistanceMeters: number
  headingErrorDeg: number
  longitudinalSpeedMps: number
  lateralSpeedMps: number
  yawRateDegPerSec: number
}
```

Initial successful-berth targets:

- longitudinal error <= 10 m;
- fender distance <= 1.5 m;
- heading error <= 3°;
- longitudinal speed <= 0.20 m/s;
- lateral speed <= 0.10 m/s;
- yaw rate <= 0.15°/s;
- all conditions stable for at least 3 seconds.

The result is `BERTH_REACHED`, not yet `ALL_FAST`; mooring belongs to P5.4.

## Contact model

Hull contact sampling must include at least:

- bow;
- forward port/starboard;
- midship port/starboard;
- aft port/starboard;
- stern.

Contact severity must be driven primarily by normal contact velocity and effective mass.

Conceptual severity:

`impact ∝ effective mass × normal velocity²`

Three regimes:

1. controlled fender contact — negligible damage;
2. hard berthing — warning / limited damage;
3. collision — material damage and no berth settlement.

## Required scenarios

### A — Alongside Berthing

Start 200–400 m from berth at approximately 4–6 kn game-scale approach speed.

Player must reduce speed, control yaw, parallelise and remove lateral velocity.

### B — Unberthing

Start alongside quay without mooring simulation.

Player must use low-speed propulsion, rudder/prop walk and thruster to clear the quay and regain the channel.

### C — Turning Basin

Start in slow ahead motion and complete an approximately 180° turn in constrained space.

This scenario exercises engine kicks, residual yaw, prop walk and thruster use together.

# Acceptance tests

## AT-01 — Deterministic replay

Repeated identical input streams produce the same final state within defined floating-point tolerance.

## AT-02 — Engine response delay

- FULL AHEAD cannot produce full shaft output in one tick.
- FULL AHEAD → FULL ASTERN must pass through a delayed neutral response phase.

## AT-03 — Rudder without flow

Stopped vessel + STOP + hard rudder causes negligible heading change.

With a low ahead order and hard rudder, propeller wash creates measurable yaw response.

## AT-04 — Residual yaw

MIDSHIPS/STOP does not instantly remove yaw rate. Counter-rudder reduces it more rapidly.

## AT-05 — Prop walk

Midships rudder + astern power produces deterministic transverse stern/yaw response according to propeller handedness.

## AT-06 — Bow thruster effectiveness

Strong at zero speed, strongly degraded by 4 kn, negligible around 5 kn and above.

## AT-07 — Class distinction

Panamax must require materially more stopping distance, turning time and manoeuvring room than Coaster.

Target normalized stopping-distance ratio:

`Panamax >= 1.8 × Coaster`

## AT-08 — Load distinction

10% vs 90% loaded Handysize must show measurable differences in acceleration, stopping and turn response.

## AT-09 — Wind and current

- unloaded high-windage vessel drifts materially more under beam wind;
- current changes SOG/COG without inventing hull yaw.

## AT-10 — Controlled berthing

A berth meeting the defined lateral/longitudinal speed, heading, yaw and position limits settles successfully after the stability interval.

A materially faster lateral impact must not settle and must produce greater damage.

## Regression gates

- no NaN/Infinity over 30 simulated minutes;
- existing campaign tests remain green;
- arrival settlement remains single-shot;
- unfinished manoeuvre reload does not settle;
- persisted attempts migrate forward;
- legacy 2D harbour remains available;
- build remains green.

## Definition of Done

P5.3 is complete only when:

1. AT-01 through AT-10 are automated and green;
2. Alongside Berthing, Unberthing and Turning Basin are playable;
3. a Handysize low-speed approach visibly requires advance planning;
4. residual surge/sway/yaw have tactical consequences;
5. prop walk and bow thruster matter to manoeuvre choice;
6. controlled contact and collision are reliably distinguished;
7. campaign integration/persistence remain intact;
8. the controls are accepted on a physical phone.

## Explicitly outside P5.3

- tug boats;
- pilots;
- mooring lines;
- dynamic harbour traffic;
- AIS and radar;
- tide and tidal prediction;
- squat and bank effect;
- detailed shallow-water hydrodynamics;
- wave/seaway model;
- anchors;
- multi-screw/azipod/Voith propulsion;
- full structural damage topology;
- final Rotterdam art.

These belong to P5.4+.

## Product gate

The final question is:

> Does the player have to think ahead about where the ship will be and how it will still be moving several control decisions from now?

If a late FULL ASTERN or hard-rudder input can still rescue most bad approaches, P5.3 is not finished.
